# general 스캐폴드

모든 유형의 뼈대다. 다른 스캐폴드 파일은 이 다섯 칸의 **이름과 순서를 그대로 두고** 칸 안에 쓸 것만 바꾼다. 그래서 어떤 입력이든 같은 자리에서 같은 종류의 정보를 찾을 수 있다.

## 섹션 순서

| # | 섹션 | 쓸 것 | 길이 한도(대화 기준) |
|---|---|---|---|
| 1 | TL;DR | ① 이것이 무엇인가 ② 핵심 동작 한 줄 ③ 가장 중요한 숫자나 제약 하나(원문에 있을 때) | 3줄 |
| 2 | 왜 중요한가 | 어떤 문제를 푸는가 / 원문이 든 이유(원문이 반사실·대안을 말하면 그것) / 누가 영향을 받는가 | 글머리 3개 |
| 3 | High-level design | 구성 요소와 그 사이의 흐름. 다이어그램 + 설명 | 노드 7개, 설명 2줄 |
| 4 | Low-level design | 핵심 경로 하나의 함수·데이터·호출 순서와 실패 경로 | 단계 10개 |
| 5 | Insights | 직관과 다른 점, 흔한 오해, 실패할 때 보이는 것, 위험 | 글머리 3~5개 |

다섯 칸 뒤에 두 줄을 붙인다: `빠진 디테일:` 과 `출처:` (SKILL.md 3절).

대화 출력의 제목 형식: `### 1. TL;DR`, `### 2. 왜 중요한가`, `### 3. High-level design`, `### 4. Low-level design`, `### 5. Insights`. 전체 50줄 이내.

## 길이 한도 읽는 법

- 줄 수는 다섯 칸 본문의 내용 줄만 센다. 빈 줄, 코드 펜스, `유형:`·`용어:`·`빠진 디테일:`·`출처:` 줄은 세지 않는다. eli5 끝 블록은 eli5.md의 한도를 따른다.
- 우선순위: SKILL.md 3절 출처 규칙 > 짧은 원문 상한(아래) > 유형 파일의 한도 > 이 파일의 한도 > 모드의 기본 배치. 단 개수는 모드의 화면 한도(html 한 화면, slides 한 장, shorts 60초)가 더 작으면 그것에 맞춰 합치고, 합친 것을 `빠진 디테일`에 적는다. 모드 배수(eli5·ste 1.5배)는 유형 파일의 한도에 곱한다. doc은 doc.md의 숫자를 쓴다.
- **짧은 원문:** 원문 본문이 1,500자 미만이다. 줄 수로 판정하지 않는다. 사본의 수집 메타데이터(id·title·source·fetched 같은 키)는 본문에 넣지 않는다. 원문 자체의 머리말 중 내용을 담은 키(message·audience 같은 것)는 본문에 넣는다. PR은 글자 수 대신 변경 규모로 본다: 추가+삭제 50줄 미만이고 바뀐 파일 3개 이하.
- **짧은 원문의 상한:** 다섯 칸 본문 글자 수로 센다(칸 제목, `유형:`·`용어:`·`근거:`·`빠진 디테일:`·`출처:` 줄, eli5 끝 블록은 빼고 센다). 모드 없음·eli5·ste는 max(원문 × 1.5, 1,200자), doc은 max(원문 × 2, 2,000자), video는 1~3분. 원문 글자 수는 PR이면 본문 + 추가·삭제 줄이다. 끝내기 전에 센다. 세는 법: 본문 줄을 뽑아 개행만 빼고 센다. 공백·목록 기호와 대화 HLD의 간선 목록은 넣고, Mermaid·SVG 소스는 뺀다(셸: `tr -d '\n' < 본문 | wc -m`).
- 짧은 원문을 줄이는 법: 같은 사실을 칸마다 되풀이하지 않는다. 원문에 없는 칸 항목은 칸마다 `원문에 없음` 줄을 쓰지 않고 `빠진 디테일`에 한 줄로 모은다. 근거는 칸 끝 한 줄에 모은다. doc은 HLD 그림 하나, LLD 표 하나, Insights로 쓴다(같은 단계를 시퀀스·글로 읽기·식별자 표에 되풀이하지 않는다).

## HLD와 LLD의 차이

|  | High-level design (HLD) | Low-level design (LLD) |
|---|---|---|
| 답하는 질문 | 무엇과 무엇이, 무엇을 주고받는가 | 그 안에서 정확히 어떤 순서로 무엇이 불리는가 |
| 단위 | 사람, 외부 시스템, 따로 실행·배포되는 단위(앱·서비스·CLI·DB·큐). 전송·프로토콜이면 이름 붙은 통로(스트림·세션)도 | 모듈·클래스·함수, 자료 구조와 필드, 메시지 |
| 넣지 않는 것 | 함수 이름, 필드 이름, 파일 경로, 수식 기호·변수·임계식 | 핵심 경로와 무관한 구성 요소 |
| C4 수준 | System Context + Container | Component·Code + 시퀀스 |
| 범위 | 전체를 한 장에 | 독자가 이해해야 할 핵심 경로 하나, 또는 바뀐 곳 |

- C4의 Container는 Docker 컨테이너가 아니다. 따로 실행·배포되는 단위를 말한다.
- HLD를 먼저 정하고, LLD는 HLD의 화살표 하나(또는 화살표로 이어진 경로 하나)를 확대한 것으로 쓴다. LLD 첫 줄에 확대한 화살표의 라벨을 HLD에 쓴 그대로 옮겨 적고, 그 라벨이 LLD 첫 단계가 나르는 것과 같은지 본다. HLD와 LLD는 같은 시스템을 다룬다. LLD 단계는 첫 줄에 적은 경로 안의 것만 쓴다. 경로 밖 단계(루프 판정·준비 단계·다른 화살표)가 필요하면 첫 줄을 넓히거나(`경로: 실행 전체(<첫 노드> → … → <끝 노드>)`. 왕복이라 처음과 끝이 같으면 가장 먼 노드를 넣어 `A → … → Z → … → A`) 그 단계에 `(경로 밖)`을 단다.
- **같은 대상의 다른 변형:** HLD 주 경로의 LLD 정보가 원문에 없으면 `원문에 LLD 수준 정보 없음`을 쓰고 있는 단계까지만 쓴다. 다른 변형(옛 방식·다른 제품·다른 설정)을 대신 확대하려면 HLD에 그 변형을 분기 조건과 함께 그리고 LLD 첫 줄에 `변형 <이름>을 확대`라고 쓴다. 한 변형에만 있는 라벨을 다른 변형의 LLD로 잇지 않는다.
- **한 실행 단위 안의 대상:** 핵심이나 바뀐 곳이 앱·서비스 하나 안에만 있으면 HLD = 그 단위 + 바깥 호출자·의존 대상 + 안쪽 구성 요소 한 단계(모듈 수준의 쉬운 이름). 클래스·타입·함수·오류 이름은 LLD로 보낸다. 원문이 이름을 붙이지 않은 안쪽 구성 요소를 노드로 만들면 HLD 설명에 "노드 이름은 into가 붙인 묶음 이름"이라고 한 번 밝힌다. 동작을 그 노드에 귀속하는 것은 원문이나 보충 근거가 있을 때만 한다.
- **노드가 2개 이하로 나오면**(예: 사용자 ↔ 에이전트 대화 하나) HLD를 내용 구조(개념·방법·주의 사이의 관계)로 그린다. 노드가 원문 소제목을 옮긴 것뿐이면(목차 그림) 다시 그린다. 대화형 how-to면 요청 → 응답 → 분기 → 복구의 고리를 그린다.
- 대안 경로를 한 그림에 합치면 경로마다 분기 조건과 결과가 돌아가는 곳을 그린다.
- LLD는 원문의 실제 식별자를 쓴다. 원문에 그 수준의 정보가 없으면 `원문에 LLD 수준 정보 없음`이라고 쓰고, 원문에 있는 단계까지만 적는다.
- 원문에 순서가 없으면(순서 없는 보고서·규칙 모음) LLD 첫 줄에 `순서: 원문에 없음(원문 절 순서)`라고 쓴다. 순서를 지어내지 않는다. 설명을 위해 실행 순서로 다시 배열했으면 `순서: 원문에 없음. 실행 순서로 재구성(추정)`이라고 쓰고 옮긴 단계마다 원문 위치를 단다.
- 처음부터 전부 자세히 그리지 않는다. 자세한 그림은 중요한 곳에만 쓴다.

## 다이어그램 규칙

- **이름이 아니라 동작을 그린다.** 화살표마다 무엇이 오가는지 라벨을 단다. 라벨 없는 화살표는 쓰지 않는다.
- **간선도 사실 주장이다.** 간선마다 발신자 → 수신자, 나르는 것(명사), 그 동작의 주체를 원문과 대조한다(fact-card.md 1절 주체 열).
  - 라벨에는 원문이 그 경로로 보낸다고 말한 것만 쓴다. 원문 여러 곳을 묶어 이름 붙였으면 `(추정)`.
  - 묶음 노드의 라벨이 묶은 항목 일부에만 맞으면 `(일부)`를 단다.
  - 사람이 하는 관문 행동(승인·수락·검토)은 그 사람 노드에서 나가는 간선으로 그린다.
  - 실행하는 쪽(런타임)과 제한하는 경계(샌드박스·프록시)를 나눈다. 경계가 결과를 보낸다고 그리려면 직접 근거를 단다.
  - 조회·대기는 요청하는 쪽에서 대상으로 그린다. 응답·알림은 원문이 실제로 전달된다고 말할 때만 반환 간선으로 그린다.
  - 왕복은 간선 둘로 나눈다. 한 간선에 보내는 것과 돌아오는 것을 함께 쓰지 않는다(세로 쇼츠의 예외는 shorts.md).
- 핵심 경로나 바뀐 곳만 강조한다. 의미 없는 장식·아이콘·색은 쓰지 않는다.
- 여러 조건(실험군·통제군, 모드, 설정)이 함께 지나가는 노드와 간선에는 한 조건에만 맞는 속성을 쓰지 않는다(공통 반환 간선은 "기능 결과 또는 오류", 예시 경로의 값은 예시라고 쓴다). 조건 차이는 화살표 라벨에 둔다.
- 본문에서 `(추정)`인 간선은 라벨에도 `(추정)`을 단다. 파일 모드에서는 점선으로 그려도 된다.
- **대화 출력의 HLD:** 코드 블록 안에 한 줄에 화살표 하나(간선 목록). 박스 그림은 한글 글자 폭 때문에 줄이 어긋나므로 쓰지 않는다. 아래는 형식 예시일 뿐 특정 시스템의 사실이 아니다.

  ```text
  사용자 ──(작업 요청)──▶ CLI
  CLI ──(대화 기록 + 도구 목록)──▶ 모델 API
  모델 API ──(도구 호출 요청)──▶ CLI
  ```

- **대화 출력의 LLD:** 번호 목록. `n. 호출자 → 피호출자(주요 인자): 하는 일 (근거)`. 반복되는 단계에는 `(반복: 조건)`을 붙인다.
  - 실패 경로는 `✗` 로 시작하는 줄로 그 단계 바로 아래에 두고, 흐름이 거기서 끝나는지(return·거절) 어느 단계로 이어지는지 적는다. 이어지는 단계 번호는 실제로 실행되는 다음 단계와 대조한다. `✗` 줄은 단계 수에 넣지 않는다.
  - `✗`는 실제 제어 흐름 분기(return·거절·다른 단계로 점프)에만 쓴다. 성공으로 일찍 끝나는 분기는 `↳ 끝:`으로 쓴다(실패로 읽히지 않게. 이 줄도 단계 수에 넣지 않는다). 값이 없을 때 기본값으로 대신하는 것(`unwrap_or_else` 같은 것)은 그 단계 설명에 조건으로 쓴다.
  - 대안 경로(특정 설정·결합 방식에서만 도는 단계)는 그 분기 줄 아래 들여쓴 하위 목록으로 쓴다. 정상 종료 다음 번호로 이어 붙이지 않는다.
  - 판정이 여러 갈래로 나뉘면 다음 단계 줄에 진입 조건을 쓴다(예: "승인을 통과하면 …"). 호출된 함수 안에서 일어나는 일은 그 호출 단계 아래 들여쓴 하위 목록으로 쓴다. 원문에 반복 근거가 없으면 따로 부르는 호출들을 하나의 반복으로 묶지 않는다.
  - 원문이 `중략`·`…`으로 자른 구간을 건너는 순서·종료·다음 단계는 쓰지 않는다. 꼭 써야 하면 `(추정)`을 단다. 본문이 생략된 분기도 그 동작을 설명하지 않는다. `aria-label`·나레이션도 같다.
  - 일어나는 단계가 원문에 없는 중단·실패(어느 단계에서나 생기는 것)는 목록 맨 아래에 `✗ (위치 원문에 없음)` 줄로 따로 둔다. 원문에 없는 복귀 지점으로 잇지 않는다. 번호 하나에 속하지 않는 주의·조언은 번호 목록을 닫은 뒤(HTML이면 `</ol>` 밖) 따로 쓴다.
- 파일 모드는 모드 파일의 형식(Mermaid, 인라인 SVG)을 쓴다. 노드·단계 한도는 같다(doc은 doc.md의 숫자).

## 칸별 메모

- **TL;DR:** 첫 줄만 읽어도 무엇인지 알게 쓴다. 형용사보다 동사를 쓴다.
- **왜 중요한가:** 구조를 외우는 것보다 구조가 왜 필요한지가 오래 남는다. 그래서 원문이 든 이유를 한 줄 넣는다. 반사실("이것이 없으면 무엇이 달라지는가")은 **원문이 반사실이나 대안을 직접 말할 때만** 쓰고 그 문장(예: "would otherwise …")을 인용한다. 원문이 "가능한 이유"만 말하면 `원문이 든 이유: …`로 쓴다. "X 덕분에 가능"을 "X 없으면 불가능"으로 바꾸지 않는다. 조건문이나 평가 문장에 "반사실" 이름을 붙이지 않는다. "A보다 B"는 비교한 대안이지 반사실이 아니다. 원문이 다른 해결책을 들면 같이 쓴다.
- **Insights:** 원문이 직접 말한 것과 원문에서 끌어낸 판단을 구분한다. 후자는 `(추정)`. 실패 경로를 다뤘다면 "실패하면 화면·로그에 무엇이 보이는가"를 한 줄 넣는다(원문에 있을 때).
- **엇갈림·충돌:** 두 문장을 엇갈림·긴장·모순·충돌로 부르기 전에 ① 대상·작업·조건·시점·평가 기준이 같은지 ② 원문 안에 둘을 함께 쓰는 법(해법)이 있는지 찾는다. `(추정)`을 붙여도 이 확인을 건너뛰지 않는다. 두 문서가 항목을 늘어놓았으면 둘 다 든 항목과 한쪽만 든 항목을 나누고, 둘 다 든 항목에만 모순을 붙인다. 결과는 셋 중 하나로 쓴다.
  - **모순:** 두 문장이 동시에 성립할 수 없다. "충돌"이라는 말은 이때만 쓴다.
  - **범위 불일치:** 제목·요약·훅이 본문보다 넓거나 좁게 말한다.
  - **관계 설명 없음:** 다른 시점·다른 대상에 대한 설명이거나, 함께 쓰는 법이 원문에 없다.
  - 대상·기준이 다른 평가는 "다른 기준의 평가"나 "장점과 비용"으로 쓴다.
  - 엇갈림마다 글머리를 따로 두고 라벨을 하나만 단다. 본문의 판정 문장이 라벨과 같은지 본다. 라벨이 "관계 설명 없음"인데 본문이 "함께 성립하지 않는다"고 쓰면 그것은 모순이다.
