# pr 스캐폴드

**적용:** PR·MR URL, `gh pr view` 결과, diff·patch, "이 PR", 로컬에 저장한 PR 사본. general의 다섯 칸 이름과 순서를 그대로 쓴다.

## 원문 읽기

- 읽기 전용만: `gh pr view <번호> --json title,body,files,commits,additions,deletions`, `gh pr diff <번호>`. 연결 이슈가 본문에 있으면 그 이슈도 읽는다.
- 댓글 작성, 승인, 병합, checkout, 테스트 실행은 하지 않는다(사용자가 따로 요청하면 제외).
- 입력이 저장된 사본이면 그 사본이 원문이다. 사본이 잘렸으면 잘린 범위를 `출처:`에 밝힌다.
- 바뀐 파일이 많으면(대략 30개 넘음) 핵심 경로의 파일만 자세히 읽고, 나머지는 `기타 변경: 파일 n개(테스트·포맷·생성 파일)` 한 줄로 묶어 LLD 끝에 둔다. n은 PR 전체의 바뀐 파일 수다. 사본이 잘렸으면 `보이는 m개 · 전체 n개`로 쓴다. 묶은 범위는 `출처:`에 밝힌다.
- **보충:** LLD·왜 중요한가에 필요한 호출자·정의·이전 동작·바꾼 이유가 diff 밖에 있으면 병합(또는 head) 커밋의 해당 파일을 읽기 전용으로 읽어 보충한다: sha는 `gh pr view <번호> --json mergeCommit,headRefOid`, 파일은 `gh api repos/<owner>/<repo>/contents/<path>?ref=<sha>`. 표시는 `(보충: <sha 7자> path:line)`(SKILL.md 3절). 도구가 없거나 사용자가 원하지 않아 보충하지 않으면 그 자리에 `(diff 밖)`이라고 쓴다.
- **줄 번호:** PR 뒤 파일 기준이다(hunk 머리 `@@ +n`에서 센다). 삭제된 줄은 `path:-n`(PR 전 파일 줄)로 쓴다. 저장된 사본의 줄을 쓰면 `raw:n`으로 구분하고, 핵심 식별자는 `path:n (raw:m)`처럼 둘 다 쓴다. 센 번호가 맞는지 그 줄의 식별자와 다시 대조한다(셸이 있으면 손으로 세지 말고 계산한다). diff에 없는 줄 번호를 지어내지 않는다.
- **작은 PR:** 추가+삭제 50줄 미만이고 바뀐 파일 3개 이하이면 general의 "짧은 원문"이다(video 1~3분 등). 바뀐 파일 수는 테스트·스냅샷·lock 파일을 빼고 센다.

## 섹션 순서

| # | 섹션 | 쓸 것 | 길이 한도 |
|---|---|---|---|
| 1 | TL;DR | 무엇을 바꿨나 / 왜 바꿨나(본문·이슈 근거, 없으면 `원문에 없음`) / 규모(파일 n개, +a −b) | 3줄 |
| 2 | 왜 중요한가 | 이 변경이 없으면 생기는 문제(버그·요구. 본문·이슈에 있을 때, 없으면 `원문에 없음`), 영향받는 쪽(사용자·API 호출자·운영), 호환성을 깨는지 | 글머리 3개 |
| 3 | High-level design | 바뀐 구성 요소를 표시한 흐름. 노드·화살표 구성이 바뀌면 전/후 두 개. 화살표가 나르는 내용(문구·값)이나 타는 분기만 바뀌면 그림 하나 + `*` + `전:` 한 줄 | 노드 7개(그림마다) |
| 4 | Low-level design | 아래 "LLD 쓰는 법". 새로 생긴 실패 경로 | 단계 10개 |
| 5 | Insights | 리뷰 포인트: 위험, 테스트가 덮지 않는 경로, 놓치기 쉬운 부수 효과, 본문 설명과 diff가 다른 곳 | 글머리 3~5개 |

## LLD 쓰는 법

- **바뀐 곳이 호출 경로 위에 있으면:** 핵심 경로의 호출 순서를 쓰고 바뀐 단계에 `*`를 붙인다. 경로 밖의 다른 핵심 변경은 그 뒤에 "무엇이 → 무엇으로" 목록(3~5개)으로 쓴다.
- **바뀐 것이 호출 경로 위에 없으면**(문구·플래그·기본값·의존 정리·리팩터): LLD 첫 줄에 바뀐 곳(HLD의 노드·화살표)을 적고, 변경 3~5개를 "무엇이 → 무엇으로"로 먼저 쓴다. 그 값이 쓰이는 경로는 원문이나 보충 근거가 있을 때만 적는다.
- **경로 전체가 새 코드면**(새 모듈·새 기능): 첫 줄에 `모든 단계 (new)`라고 쓰고, 기존 파일을 고친 단계에만 `*`를 붙인다.
- 테스트 변경은 번호 단계에 넣지 않는다. Insights(테스트가 덮는 것·덮지 않는 것)나 근거에 쓴다.
- **LLD 자리가 작은 모드**(eli5·html·slides·shorts): 변경 목록 형식이면 LLD 자리를 `바뀐 것(전 → 후)` 3줄 이하와 `쓰이는 경로` 3단계 이하로 나눈다. 두 목록을 한 번호 목록에 섞지 않는다. 호출 경로 형식이면 모드의 단계 한도(html 6단계 등)에 맞춰 단계를 합치고 합친 것을 `빠진 디테일`에 적는다.
- **작은 자리의 필수 조각:** html의 "왜 중요한가" 한 줄 끝에 `호환성: …`을 둔다. test의 `QUIZ.scope`에 `파일 n개 · +a −b`를 넣는다.
- 단계마다 `path:line`을 단다.

## 다이어그램 규칙

- HLD: 바뀐 노드 이름 뒤에 `*`, 새 노드는 `(new)`, 없어진 노드는 `(removed)`를 붙인다. 바뀐 것이 노드가 아니라 화살표(의존·호출이 생기거나 없어짐)나 화살표가 나르는 내용(오류 문구·값)이면 그 화살표 라벨에 같은 표시를 붙인다.
- 한 프로세스 안의 변경은 general의 "한 실행 단위 안의 대상" 규칙을 따른다. 아래는 형식 예시일 뿐 특정 PR의 사실이 아니다.

  ```text
  사용자 ──(입력)──▶ 터미널 앱
  터미널 앱 ──(마크다운 본문)──▶ 렌더러*
  렌더러* ──(화면 줄)──▶ 터미널 앱
  ```

  `렌더러` 안의 함수·타입·오류 이름은 LLD에만 쓴다.
- 전/후 두 그림이면 노드 이름을 같게 맞춰 차이만 보이게 한다. html·slides에서 전/후를 보이는 법은 각 모드 파일에 있다.

## general에서 바꾼 점과 이유

- TL;DR에 변경 규모를 넣었다 — 리뷰에 걸릴 시간을 먼저 가늠하게 하려고.
- 왜 중요한가에 호환성을 넣었다 — 호환성을 깨는 변경은 다른 모든 판단보다 앞선다.
- HLD는 전체 구조보다 바뀐 곳을 표시한다 — PR 독자는 무엇이 달라졌는지를 찾는다.
- LLD에 `path:line`을 단다 — 리뷰는 결국 코드 위치로 돌아가야 끝난다.
- LLD를 바뀐 곳의 모양에 따라 둘로 나눴다 — 호출 경로를 바꾼 PR과 값·문구만 바꾼 PR은 이해할 단위가 다르다.
- 작은 자리에서도 변경 목록과 쓰이는 경로를 나눈다 — 둘을 한 번호 목록에 섞으면 변경·테스트가 실행 순서처럼 읽힌다.
- Insights를 리뷰 포인트로 바꿨다 — PR 이해의 끝은 승인할지, 무엇을 고쳐 달라고 할지의 결정이다.
- 본문과 diff의 차이를 본다 — PR 본문은 작성자의 주장이고 diff가 실제 변경이다.
