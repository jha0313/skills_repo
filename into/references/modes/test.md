# test 모드

**목표:** 읽은 것을 정말 이해했는지 시험 보듯 확인한다. 형식만 바꿔 다시 읽으면 이해했다는 느낌만 남기 쉽다. 그래서 답을 보기 전에 **먼저 예측**하고, 그다음 답과 피드백을 본다.

**출력:** `into-out/<slug>-test.html`. [assets/test.html](../../assets/test.html)을 복사하고 `QUIZ` 데이터만 채운다(페이지 제목도 `QUIZ.title`이 정한다). 동작 코드는 고치지 않는다.

## 문항 구성

기본 8문항(사용자가 정하면 5~10문항. 짧은 원문(general.md)이면 5~6문항이고 "왜 중요한가"는 1문항). 스캐폴드 칸에 맞춰 나눈다.

| 칸 | 문항 | 묻는 것 |
|---|---|---|
| TL;DR | 1 | 이것이 무엇을 하는가 |
| 왜 중요한가 | 2 | 인과 1개 + 반사실 1개("이것이 없으면 무엇이 달라지나?"). 반사실은 원문이 반사실·대안을 직접 말할 때만 낸다. 아니면 인과 2개. 둘째 인과는 원문의 이유를 새 상황에 적용하게 묻는다(조건이 바뀌면 결과가 어떻게 되나). 이유를 그대로 되묻는 문항은 인과로 세지 않는다 |
| High-level design | 2 | 구성 요소의 역할, 흐름의 방향·순서 |
| Low-level design | 2 | 호출 순서나 데이터, 실패 경로 |
| Insights | 1 | 직관과 다른 것 또는 흔한 오해 |

사용자 스캐폴드면 칸마다 1~2문항으로 나눈다.

## 문항 형식

- `choice`: 보기 3~4개, 정답 1개. `answer`는 0부터 센 번호다. 화면에는 보기 앞에 A·B·C·D가 붙는다(`answer: 0` = A).
- `predict`: 먼저 내 말로 예측을 쓴다 → 모범 답과 채점 기준을 본다 → 스스로 맞음/틀림을 고른다. **최소 2문항은 predict**로 낸다(내 말로 설명하기).
- 문자열에는 마크다운을 쓰지 않는다. 코드·식별자만 백틱으로 감싼다. 템플릿이 `` `x` ``를 코드 글꼴로 보인다.

```js
const QUIZ = {
  title: "<주제> 이해 확인",
  notice: "",   // 비공개 원문이면 SKILL.md 4절의 한 줄. 공개 원문이면 빈 문자열
  source: "<원문 링크·경로>",
  scope: "<읽은 범위>",   // 비공개 안내 문구를 여기에 넣지 않는다
  missing: "<이 퀴즈가 다루지 않은 디테일>",
  questions: [
    { section: "High-level design", type: "choice", q: "<질문>",
      options: ["<보기>", "<보기>", "<보기>"], answer: 2,
      explain: "<C가 정답인 이유 + A·B가 틀린 이유 한 줄씩>", source: "<근거 위치>" },
    { section: "왜 중요한가", type: "predict", q: "<질문>",
      model: "<모범 답>", explain: "<필수 ① … ② … — 둘 다 있으면 맞음>", source: "<근거 위치>" }
  ]
};
```

## 문항 쓰는 규칙

- **원문 문장으로 답이 정해지는 문항만 낸다.** 원문 문장에는 원문의 코드 줄도 든다(코드의 제어 흐름에서 바로 읽히는 답이면 근거에 그 줄을 단다). 정답 근거가 `(추정)`·`(불확실)`·보충 자료뿐이거나, 앞선 결과물(도식·요약)의 해석이면 내지 않는다. 다른 모드가 `(불확실)`로 둔 사실을 정답으로 확정하지 않는다. 원문이 직접 말한 내용을 오답으로 두지 않는다(조건마다 동작이 다른 원문 — 코드·명세·설정 — 은 다른 조건에서 참인 동작을 오답으로 쓸 수 있다. 문항에 적은 조건에서는 거짓이어야 하고, 해설에 그 조건을 적는다).
- 코드 원문이면 정답을 정하기 전에 같은 이름·같은 조건에서 다른 결과가 나오는 분기(다른 핸들러·다른 상태·다른 설정)를 하나 찾아본다. 있으면 전제에 넣거나 문항을 바꾼다. 흔히 빠지는 전제: 충돌하는 다른 규칙이 없음, 만료·권한 실패 없음, 알림·오류의 종류, 하위 폴더·파일 종류, 0개인 경우, 원래 설정값. 답을 정하는 전제 조건(설정·상태·대상)을 문항에 모두 적고 주체를 분명히 쓴다. 판정 함수의 값을 묻는지 실제 실행 결과를 묻는지 나눈다. 실행 결과를 물으면 그 판정 뒤에 결과를 바꾸는 분기의 조건까지 전제에 적는다.
- 오답 보기는 그럴듯해야 한다: 흔한 오해, 쉬운 설명에서 빠진 디테일, 헷갈리기 쉬운 이웃 개념. 말이 안 되는 보기는 쓰지 않는다. 오답 보기마다 원문 전체와 대조해, 문항에 적은 조건에서 그 보기를 지지하는 곳이 있으면 바꾼다. 오답 해설은 원문의 한정어를 그대로 인용한다.
- **보기 길이로 답이 보이지 않게 한다.** 길이는 화면에 보이는 글자로 센다(백틱 제외, 공백 포함). 정답 ≤ 오답 평균 × 1.3, 정답 ≥ 오답 평균 × 0.5(정답이 짧아 눈에 띄면 오답도 같은 형식으로 맞춘다). 정답이 가장 긴 보기(동률 포함)인 문항은 choice 문항의 1/3 이하로 한다(나머지는 올린다: 4문항이면 2개까지). 정답이 혼자 가장 짧은 보기인 문항도 같다. 모든 보기 길이가 같은 문항(순서 문항 등)은 이 셈에서 뺀다.
- **정답 위치는 내용과 상관없이 먼저 정하고, 그 자리에 정답을 쓴다.** 셸이 있으면 slug를 시드로 뽑는다(인자는 choice 문항마다 보기 수):
  `python3 -c "import random,sys;random.seed(sys.argv[1]);print(' '.join('ABCD'[random.randrange(int(n))] for n in sys.argv[2:]))" <slug> 4 4 3 4 4 4`
  같은 위치가 3번 연속 나오면 셋째만 옆 자리로 옮긴다. 한 자리가 choice 문항의 절반을 넘어도 넘친 것을 옮긴다. 셸이 없으면 직접 정하되 Q1을 B·C에 두는 습관과 고정 주기(ABCD…, CABD…)를 피한다.
- 질문 문구에 정답이나 채점 기준의 핵심어를 넣지 않는다.
- **앞 문항이 뒤 문항의 답을 알려 주지 않게 한다.** 같은 주제의 choice와 predict가 있으면 predict를 먼저 둔다. 한 사실이 여러 문항의 답이 되면 해설에서 그 사실을 줄인다. 오답 보기에 다른 문항의 정답 문장을 주체만 바꿔 쓰지 않는다. 해설의 범위 진술("두 경우뿐")·역할·순서 설명도 뒤 문항의 답이 될 수 있다.
- **회상 문항은 퀴즈당 2개 이하.** 회상 = 원문 문장·이유·숫자를 그대로 되묻기. "어디에 나오나"는 묻지 않는다. 사용기·의견 글이면 조건을 바꿔 선택 이유를 적용하거나 근거의 한계를 판단하게 한다. 규칙·방법을 다룬 원문이면 "이 상황에서 원문 규칙대로라면?" 적용 문항을 2개 이상 낸다.
- 해설은 보기를 글자(A·B·C)나 보기 문구로 가리킨다.
- **predict는 인과·적용·반사실을 묻는다.** 머리말·숫자·개별 댓글 외우기를 묻지 않는다. 반사실 predict는 원문이 반사실을 직접 말할 때만 낸다.
- **predict 채점 기준은 맞음/틀림이 갈리게 쓴다:** `필수: ① … ② …`처럼 필수 요소와 개수를 적는다. "셋 중 둘", "반만 맞음" 같은 부분 점수 문구를 쓰지 않는다. 필수 요소마다 원문 문장 하나를 짝짓는다. `채점 기준`이라는 말은 화면이 붙이므로 `explain`에 쓰지 않는다. 필수 요소만 채우고 핵심 동작을 빠뜨린 답이 통과하지 않는지 본다. 원문을 넘는 조건을 요구하지 않는다. "원문이 밝히지 않는다"는 조건은 원문 전체를 검색해 전혀 없을 때만 쓴다. 원문이 근거를 여럿 들면 그중 하나로 맞게 하거나, 질문이 근거 하나를 지정한다. 모범 답이 자기 기준을 통과하는지 채점해 본다.
- 보기 안의 숫자는 가리키는 대상(전체·부분)까지 원문과 대조한다.
- 용어 암기보다 인과·순서·실패를 묻는다. 계산 하나로 풀리는 문항은 인과·실패를 묻도록 바꾼다.

## 템플릿이 처리하는 동작

- 한 번에 한 문항. 보기를 고르거나 예측을 쓰기 전에는 `확인` 버튼이 꺼져 있다.
- `확인` 뒤에는 입력이 잠기고 정답·해설·근거가 나온다.
- `QUIZ.notice`가 비어 있지 않으면 머리 맨 위에 한 줄로 보인다.
- 끝에 점수와 틀린 문항 목록, `빠진 디테일`과 `출처`(원문·읽은 범위), `틀린 문제만 다시` 버튼이 나온다.
- 다른 페이지 안(iframe)에서 열리면 전체를 한 번에 푼 점수와 `section`별 점수를 바깥에 보낸다(domain-expert 허브가 받는다). 혼자 열면 아무것도 보내지 않는다.
- 외부 요청 없이 파일 하나로 동작한다.

## 점검

- [ ] 문항 수와 칸별 배분이 위 표와 맞다. predict가 2개 이상이다.
- [ ] 모든 문항에 `explain`과 `source`가 있다. `QUIZ.scope`와 `QUIZ.missing`을 채웠다.
- [ ] `answer` 번호가 실제 정답 보기를 가리킨다.
- [ ] 보기 글자 수를 화면 기준으로 셌다: 오답 평균 × 0.5 ≤ 정답 ≤ 오답 평균 × 1.3, 정답 = 가장 긴 보기(동률 포함)인 문항 ≤ choice의 1/3.
- [ ] 정답 위치를 먼저 정한 순서대로 두었다. 같은 위치 3번 연속이 없다. 모범 답이 자기 채점 기준을 통과한다.
- [ ] **누출 점검:** 첫 문항 화면에 함께 보이는 글(제목·`scope`·`source`·칸 이름)만 읽고 고를 수 있는 보기가 없는지 본다(`scope`에 단계 순서를 쓰지 않는다). 문항을 순서대로 읽으며 해설·보기(오답 포함)마다 뒤 문항 정답의 핵심어를 검색했다. predict마다 필수 요소를 앞 문항의 질문·보기·해설에서 찾았다. 그다음 앞 문항의 질문·보기·해설만 보고 뒤 choice 문항을 풀어 봤다. 원문을 덮고 질문과 보기만 읽어도 본다(정답만 질문의 낱말을 되풀이하거나, 정답만 양면을 말하거나, 보기 종류가 혼자 다르면 같은 구조로 고친다). 풀리거나 나오면 해설을 줄이거나 순서를 바꿨다.
- [ ] 앞 문항을 낸 뒤 보이는 것 전부(`model`·`explain`·근거)를 펼쳐 놓고 다음 문항을 풀어 봤다.
- [ ] 사용자가 질문을 줬으면 질문이 지목한 경로마다 그것이 **정답인** 문항이 있다(보기에 이름만 나온 것은 세지 않는다).
- [ ] 회상 문항이 2개 이하다.
