# 설계 문서 (RFC · ADR)

읽는 사람이 궁금한 것: 무슨 문제인가 · 무엇으로 정했나 · 왜 다른 안은 아닌가

| 단계 | 칸 | 채울 것 |
|---|---|---|
| 간단히 | 한 줄 요약 | 무엇을. 동사가 상태다: `제안했다` · `정했다` · `접었다` |
| | 문제 | 지금 겪는 장면 하나 |
| | 전체 구조 | 그림: 정한 뒤의 흐름 |
| | 고른 안과 버린 안 | 고른 것과 버린 것 다섯까지. 안마다 이유 한 줄 |
| | 트레이드오프 | 하나씩. 좋은 것만 적지 않는다 |
| 자세히 | 목표와 비목표 | 목표와, 할 수도 있었지만 뺀 것 |
| | 대안 비교 | 위 안들을 같은 기준으로 재는 표. 문서가 말한 칸만. 남은 안도 여기 |
| | 상황별 동작 | 표: 이럴 때 · 이렇게 |
| | 열린 질문 | 열린 질문과 누가 정하나 |
| 아주 자세히 | 상세 설계 | 데이터·API·순서를 실제 이름으로 |
| | 공통 관심사 | 보안, 개인정보, 운영, 비용 |
| | 배포와 롤백 | 배포 순서와 되돌리는 법 |

- 그림: 지금 흐름과 정한 흐름이 다르면 달라진 선만 색.
- 실수: 문서가 안 말한 칸을 추측으로 채우지 않는다. 빈칸은 빈칸.
- 참고한 구조: [Design Docs at Google](https://www.industrialempathy.com/posts/design-docs-at-google/)(대안이 가장 중요한 칸 중 하나), [ADR](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)(상태와 결과, 나쁜 결과까지)
