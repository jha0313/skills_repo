## model
- 참고: 바로 앞 에이전트 답, 개념, 다른 유형에 안 맞는 글. 앞 답을 바꿀 때 그 답의 확실성(아마·확인 안 됨)을 그대로 둔다. 노드는 원문 소제목이 아니라 일을 하는 것으로 고른다.

## 예
**일반 글·답 · 프롬프트 캐싱** — 요청의 앞부분이 전에 저장해 둔 것과 똑같으면, API가 그만큼을 다시 처리하지 않고 이어 쓰는 기능(아래는 Claude API 기준)

**왜** · 모델은 요청 사이에 기억하지 않아 앱이 매번 전체를 다시 보낸다 · 캐싱이 없으면 API도 매번 전체를 다시 처리한다

```
앱 ─(매번 전체: 도구 → 시스템 → 대화, 저장 지점 표시)▶ API
API ─(저장 지점까지의 앞부분이 있나? 뒤로 최대 20칸)▶ 캐시
캐시 ─(있음: 이어 쓸 앞부분)▶ API
API ─(없음: 전체 처리 뒤 저장 지점에 저장)▶ 캐시
```

| 이러면 | 이렇게 |
|---|---|
| 앞부분이 그대로 | 뒤만 처리. 읽은 만큼은 보통 입력 값의 0.1배(5분짜리 저장은 1.25배) |
| 앞쪽 한 군데가 바뀜 | 그 뒤가 전부 다시. 도구 정의를 바꾸면 전체가 다시 |
| 매번 바뀌는 블록(시각 등)에 저장 지점 | 매번 저장 값만 내고 한 번도 못 읽는다 |
| 너무 짧음(모델마다 512~4,096 토큰) | 오류 없이 캐싱이 안 된다 |
| 요청 시작 뒤 5분 지남(쓸 때마다 갱신) | 사라진다. 응답을 만드는 시간도 5분에 든다 |
| 같은 요청을 동시에 보냄 | 첫 응답이 시작되기 전에는 못 나눠 쓴다 |

**조심** 됐는지는 `usage`로 본다. 읽은 양과 저장한 양이 둘 다 0이면 안 된 것이다
