# into 설계 — 무엇을 왜 이렇게 했나

## 한 줄

원문 하나를 **한 번만 읽고**(`model.json`), 유형마다 정해진 틀로 모드만 바꿔 여러 번 꺼낸다. 세기·검사·배치는 스크립트, 무엇이 중요한지와 문장은 에이전트.

## 한 바퀴

```text
사용자      into eli5 <입력> ─(입력·모드)▶ 스크립트
스크립트    start: 유형·크기·공개 여부, 원문에서 셀 것을 센다 ─(작업 지시 한 장 · pack.md)▶ 에이전트
에이전트    읽고 고른다 ─(model.json: 사실·간선·단계 + 근거)▶ 스크립트
스크립트    check: 근거 줄·숫자·이름·조건을 원문과 맞춘다 ─(FAIL이면 되돌린다)▶ 에이전트
에이전트    그 모드의 칸만 쓴다 ─(<모드>.json)▶ 스크립트
스크립트    render: 길이·배치·그림·근거 줄. FAIL이면 결과를 쓰지 않는다 ─(결과)▶ 사용자
사용자      into interactive ─(다른 모드)▶ 같은 model.json부터
```

## 누가 무엇을 하나

| 정해진 일 → 스크립트 | 판단 → 에이전트 | 취향 → 사람이 고치는 표 |
|---|---|---|
| 유형 고르기(점수, 비기면 둘을 보여 준다) | 독자의 첫 질문 셋에 답하는 사실 고르기 | 칸 이름·순서·한도(`formats/`) |
| 원문에서 셀 것(파일·줄·장·영상 시각) | 주장을 어디까지 좁힐지, 무엇을 뺐는지 | 새 유형 추가 |
| 근거 줄·숫자·이름 대조 | 처음 듣는 사람이 읽을 문장 | 발표 브랜드(CSS 변수) |
| 길이·표 모양·그림 배치·출처 줄 | 비유, 퀴즈의 오답, 대본 | |
| 파일 이름, 다시 쓰기, 비공개 안내 | 원문이 엇갈릴 때 무엇을 믿나 | |

## 결정과 이유

| # | 결정 | 왜 | 버린 것 |
|---|---|---|---|
| 1 | 읽기 결과를 `model.json` 하나로, 모든 모드가 함께 쓴다 | 모드마다 다시 읽으니 이름·숫자·그림이 서로 달랐다 | 모드마다 따로 읽기 |
| 2 | 정해진 동작은 스크립트 | 길이·출처 규칙을 글로 쓰면 지켜지지 않았다. 읽을 지침만 2.8만~4만 자였다(지금 작은 글 eli5 약 6천 자, PR 약 8천 자) | 더 긴 지침 |
| 3 | 틀은 Markdown 표 | 사람이 행을 고치면 스크립트가 따른다. 셸이 없는 곳에서도 읽힌다 | JSON 스키마, 코드 속 템플릿 |
| 4 | 유형마다 모양은 다르게, 칸 순서는 같게(한 줄 → 왜 → 그림 → 도는 순서 → 조심) | 한 번 익히면 어디를 볼지 안다. 모양까지 같게 하면 떨어진다(커뮤니티 글: 카드 50% → 줄+대가 81%) | 모든 유형에 같은 틀 |
| 5 | 짧은 쪽이 기본, 한도는 최대치만 | 길다고 더 이해되지는 않았다(저장소 구역 6,067자와 1,074자가 같은 3/8 안팎) | 최소 분량, 모든 칸 채우기 |
| 6 | 조건을 지우지 않고 주장을 좁힌다 | 짧게 줄일 때 가장 먼저 사라지는 것이 조건이고, 그때 틀린 말이 된다 | 조건을 각주로 |
| 7 | FAIL은 기계가 확실히 아는 것만, 뜻은 WARN | 조건 낱말 검사를 FAIL로 두니 맞는 문장을 고치느라 시간을 썼다 | 뜻까지 자동 판정 |
| 8 | 근거는 id로, 출처 줄은 스크립트가 | 에이전트가 손으로 쓴 줄 번호가 자주 어긋났다 | 본문에 줄 번호 쓰기 |
| 9 | 저장소는 지도 → 구역 → 코드 | 4만 줄을 한 화면에 담으면 아무것도 안 남는다 | 한 장 요약 |
| 10 | html·interactive가 그림 부품 하나를 함께 쓴다 | 매번 새로 그리면 겹침·빈 곳이 생긴다 | 에이전트가 SVG 쓰기 |
| 11 | 슬라이드는 장마다 그림 하나, 부품 11가지 | 글머리 장은 말로 하면 되고 그림 장은 봐야 안다 | 글머리 덱 |
| 12 | 다음 모드는 부를 때만 | 안 읽을 것을 만들면 확인할 것만 는다 | 한 번에 모두 만들기 |
| 13 | 표준 라이브러리만, Python 3.9+ | 설치가 막히면 검사도 막힌다 | 의존성 |

## 유형마다 고른 모양

| 유형 | 고른 모양 | 같이 시험한 다른 모양 |
|---|---|---|
| PR | 상황 하나의 전 → 후 두 줄 15/16 · 457자 | 질문-답 15 · 상황 표 14.5 · 이야기 15.5(그림이 없다) |
| 저장소 | 상황 → 결과 표 3.5/8 · 1,074자 | 한 바퀴 2.5 · 지도 2 · 질문-답 1.5 |
| 설계 문서 | 길 + 이러면 → 이렇게 88% → 94% · 647자 | 전후 그림 81% · 질문-답 71% |
| 논문 | 결과 표 먼저 94% · 548자 | 이야기 순서 67% · 주장 사다리 91% |
| 영상 | 질문 → 답 시간줄 94% · 973자 | 장면 이름만 71% · 핵심 셋 73% |
| X·스레드 | 주장마다 한 줄 + 하나를 끝까지 85~92% | 근거 센 순 60~79% · 주장 나무 67~73% |
| 커뮤니티 글 | 입장 + 사례 둘 + 갈리는 까닭 90% · 947자 | 입장만 56% · 둘 대조 54% |
| 파일 하나 | 넣는 것 → 나오는 것 14/16 · 671자 | 해부도 8.5 · 질문-답 8 |
| 스킬 | 레인 + 어긋날 때 7.5/8 · 947자 | 계약·이야기 5.5 |
| 그 밖 | 길 + 이러면 → 이렇게 | 질문-답(그림과 조건이 빠진다) |

이 점수는 **고를 때 본 원문**의 것이다. 자세한 것은 각 `formats/*.md` 끝의 `왜` 주석.

## 잰 값 — 처음 보는 원문

설명만 읽은 모델 독자가 8문항(첫 질문 2 · 속 동작 3 · 조건 2 · 원문에 없는 것 1)에 답한다. 문항은 GPT가 원문만 보고 썼고, 만드는 에이전트는 문항도 점수도 못 봤다. 이전 판은 길이 한도가 없던 0.7이다.

| 처음 보는 원문 | 설명 없이 | 0.7 eli5 | 1.0 eli5 | 0.7 html | 1.0 html |
|---|---|---|---|---|---|
| 1회차 12편 | 42% | 78% · 4,630자 | 74% · 1,316자 | 66% | 70% |
| 2회차 11편(0.7도 있는 것) | 44% | 82% · 4,237자 | 74% · 1,219자 | 72% | 77% |

| 2회차 문항 | 첫 질문 | 속 동작 | 조건 | 없는 것 |
|---|---|---|---|---|
| 0.7 eli5 → 1.0 eli5 | 70 → 73% | **88 → 65%** | 77 → 73% | 100 → 100% |
| 0.7 html → 1.0 html | 61 → 73% | 73 → 74% | 66 → 73% | 100 → 100% |

- 글자를 3할로 줄이며 잃은 것은 **속 동작**이다. 첫 질문과 조건은 거의 지켰다. 속 동작이 필요하면 doc이다.
- 2회차에서 html(77%)은 eli5(74%)와 비슷했다. 3점 차이는 우연일 수 있다.
- 규칙만 나열된 지시문 하나(2.5/8)와 방법 논문(5/8)이 가장 약했다. 2회차 뒤 틀의 문구를 고쳤고 다시 재지 않았다.

## 아직 못 하는 것

- **뜻은 못 본다.** 근거 줄·숫자·이름이 원문에 있는지까지만 본다. 원문을 잘못 읽은 문장도 통과할 수 있다.
- 큰 저장소 구역은 여전히 약하다. 짧은 설명 하나로 덮이지 않는다.
- 시험 독자는 사람이 아니라 모델이고, 문항은 원문당 8개다. ±몇 점은 우연이다.
- interactive·test·shorts·video가 **배움을 늘리는지**는 재지 않았다. 열리고 눌리는지, 사실이 맞는지만 봤다.
- STE는 문장 규칙만 본뜬 것이다. 표준 사전과 대조하지 않는다.
